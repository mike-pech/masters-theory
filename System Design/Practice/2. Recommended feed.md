# Лабораторная работа №2: Проектирование рекомендательной ленты для социальной сети 

## Постановка задачи 

> К вам обратился Product Owner популярной социальной сети, с целью обеспечить доступ пользователя к контенту даже на парковке. Ваша задача – спроектировать архитектуру сервиса ленты постов для социальной сети. Пользователь подписывается на авторов, видит их новые посты в своей персональной ленте, может открывать комментарии и получать уведомления о новых событиях почти в реальном времени.
## Функциональные требования:

1. Регистрация/логин, управление профилем. 
    
2. Подписка/отписка на авторов.
    
3. Публикация постов (текст + опциональные медиа-ссылки).   — не нужны хранилища S3 — посты plain text
    
4. Просмотр персональной ленты с бесконечной прокруткой (пагинация по курсору, а не по offset).
    
5. Добавление и чтение комментариев к постам.
    
6. Уведомления в реальном времени о новых постах подписок и новых комментариях к моим постам. 
## Нефункциональные требования:

1. Низкая задержка чтения ленты: p95 < 150 мс для партии из 20 элементов.
    
2. Высокая пропускная способность записи комментариев (бурсты до 10k RPS без 5xx).
    
3. Горизонтальное масштабирование ключевых компонентов.
    
4. Устойчивость к сбоям брокера/воркеров: события не теряются
    
5. Идемпотентность обработчиков событий и безопасная повторная доставка

- Хранилище ленты
	> Лента представляет собой категоризированный (Новое, Популярное и т.д.) контейнер ссылок на посты, подобранные для конкретного пользователя (User_ID)
	> 
    > Ленту скорее всего будет формировать отдельный сервис с рекомендательным алгоритмом, поэтому нужно сохранить гибкость алгоритма. Допустим, эту ленту делает отдельный сервис, который подгружает и анализирует посты с централизованной БД сервиса ленты — шардированной РСУБД (например PostgreSQL) 
    > 
    > Тогда для каждого пользователя на чтение предоставим N постов, которые будут подгружаться как самые релевантные из сервиса рекомендаций. Пусть это будет размер батча × 5 = 20 × 5 = 100 постов
    > 
    > Для быстрого обновления данных к актуальным постам в регионе кэша, но также для быстрой записи на базу данных, используется Write Back с короткой задержкой 

- Комментарии: схема под запрос «N последних по посту, сортировка по времени».
	> Для подгрузки комментариев 
    >  Стратегия Write Back предоставляет очень большую скорость работы с меняющимся постом (когда на него ставят реакции и пишут комментарии сразу после публикации), поэтому хорошо подойдёт под этот сценарий
    >  
    >  При загрузке поста в кэш с базы данных также берутся N самых популярных и новых комментариев (Eager Loading)
    
- Опишите, что и где кэшируется для гидратации постов по ID.
    > В кэше для каждого пользователя в регионе предоставлено место для 100 свежих ID постов с коротким TTL
    > При проверке ленты пользователь запрашивает батчи по 20 постов из ленты
    > 
    > Если TTL постов закончился или случился cache miss (пользователь исчерпает 100 постов), запрос идёт к сервису формирования ленты, который из централизованного хранилища подтягивает ещё 100 свежих ID постов
    > 
    > Получив ID постов, клиент запрашивает их у сервиса, который также смотрит их сначала в кэше, а потом подгружает с централизованной БД то, что не нашлось в кэше 

3. Технические решения (сравнение и выбор)
>	Для централизованного хранения постов в сервисе ленты применим **PostgreSQL** с шардированием — это сильно улучшит производительность с (ранее высчитаным) большим объёмом данных и позволит избежать проблемы знаменитости на уровне базы данных — контент знаменитости, занимающий большое место в базе скорее всего распределится по разным шардам, минуя проблему горячих ключей
>	
>	Для кэширования записей и большинства чтений применим Redis/Valkey — будем кэшировать как ленты пользоватлей, так и самые популярные и актуальные посты в регионе — те, которые пользователи из этого региона публикуют
>	Для быстрого обновления кэша поставим короткий TTL и во избежание проблемы N+1 будем использовать стратегию Eager Loading — С каждым постом мы также кэшируем N самых популярных и новых комментариев

- Стратегия формирования ленты
    > Обычно лента формируется из рекомендаций, которые подгружаются в кэш как контейнер ID постов, подобранных для пользователя. Далее, при заходе в ленту новостей, ID запрашиваются с кэша, и подгружаются с базы данных при cache miss 
    > 
    > Новые посты сразу доступны в своём актуальном регионе, так как пишутся сразу в кэш — Write Through — и отправляются подписчикам при помощи Push-модели 
    > 
    > Чтобы избежать проблемы знаменитостей воспользуемся **гибридной моделью** — пользователи с более чем 10К подписчиков переходят на модель pull для досылки постов — уведомления всё ещё посылаются как было указано (т.к. обрабатываются сторониим сервисом), но сами посты в кэшах не подгружаются — вместо этого они грузятся только с обновлением ленты. Для других пользователей остаётся стратегия push
    > 
    > Как трейдофф гибридной модели — для популярных пользователей имплементировать Write Back с быстрым реагированием на новые лайки и комментарии к посту, а для менее популярных — Write Through для простой подгрузки в ленты "Рядом с вами"
    
- Пагинация для infinite scroll	— на основе курсора
    > Далее, по курсору (SCAN в Redis) выбираются самые новые и популярные посты (новизна + просмотры/рейтинг) среди кэшированных ID. При отсутствии этих постов в кэше, делается запрос на основную БД

- Outbox/Transactional messaging
    > Для того, чтобы обеспечить идемпотентную (много запросов — одно изменение) и надёжную (сохранение в случае сбоя даже Kafka) запись в кэше и БД, мы используем Kafka с паттерном Outbox
    > 
    > Асинхронная запись изменений в БД увеличит пропускную способность и надёжность транзакций, но всё ещё не застраховано от случаев сбоя в брокере сообщений — даже с учётом внутренней идемпотентной обработки Kafka синхронизацию с БД можно потерять в случая сбоя брокера (сервис не поймёт какие сообщения не обработал брокер)
    > 
    > Поэтому в БД в таблицу Outbox мы сохраняем сообщение о новом посте, чтобы потом сохранить лог действия с постом и отправить соответствующее событие сервису уведомлений. Только после полной обработки в этом цикле мы помечаем это событие как завершённое или откатываемся, если получили ошибку на любом этапе обработки
    
- Идемпотентность и повторная доставка
    > Также паттерн Outbox обеспечит доставку постов ровно 1 раз, если не считать сбои сети, которые никогда не гарантируют 100% доставку сообщения (проблема 2 генералов)
    
- Гидратация: порядок источников (кэш → сервис постов), размеры батчей, таймауты и деградация.
    >  Батчи для клиента могут быть по 20 постов — plain-text контент лёгкий, и (по условию "с парковки") скорее всего будет запрашиваться с мобильного клиента, который с головой покроют эти 20 постов
    
- Бэкап/восстановление и репликация для разных хранилищ.
    > Бэкап основной БД можно сделать путём простой репликации Active-Passive — в приоритете запись, чтения редкие (только в случае cache miss) — с 3 репликами — стандартное правило 3-2-1 — 3 инстанса, 2 в инфраструктуре (1 основной, 1 быстрый бэкап) и 1 сторониий бэкап на случай отказа основной ноды
    > 
    > Кэши нужно развернуть по принципу Active-Active, т.к. важна не только низкая задержка, но и большая пропускная способность
