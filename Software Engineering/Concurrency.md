Современные системы всё больше и больше уходят в многоядерность и современный софт тоже больше следует направлению на параллельное исполнение кода. Первыми примерами параллельно исполняемых программ были как раз Операционные системы!

> [!WARNING] Распараллеливание работы — самый простой способ ускорить работу
> НО не всю работу нужно распараллеливать. Да и даже если для задачи требуется параллельное исполнение — нужно быть осторожным
> 
# Введение
## API

```c
#include <stdio.h>
#include <assert.h>
#include <pthread.h>
#include "common.h"
#include "common_threads.h"

void *mythread(void *arg) {
	printf("%s\n", (char *) arg);
	return NULL;
}

int
main(int argc, char *argv[]) {
	pthread_t p1, p2;
	int rc;
	printf("main: begin\n");
	Pthread_create(&p1, NULL, mythread, "A");
	Pthread_create(&p2, NULL, mythread, "B");
	// join waits for the threads to finish
	Pthread_join(p1, NULL);
	Pthread_join(p2, NULL);
	printf("main: end\n");
	return 0;
}
```
Пример использования двух потоков в C при помощи хэдера `pthread.h`

Мы создаём переменные соответствующих структур данных и запускаем их со ссылкой на процедуру `mythread`, а потом ждём выполнения через `Pthread_join` (в данном случае они ничего не возвращают, поэтому ставим `NULL`)

В коде всё просто, а на деле в программе мы теряем **детерменированность** — сначала может выполниться поток A и потом поток B, или наоборот — в зависимости от того, как их распределеит планировщик задач
## Память

![[Pasted image 20260227130654.png]]
В параллельных программах потоки делят область с кодом и кучу, но каждый поток имеет свой изолированный стек

Вследствие чего другой популярный пример проблем параллельности — инкрементация счётчика

```x86
mov 0x8049a1c, %eax
add $0x1, %eax
mov %eax, 0x8049a1c
```

Здесь мы перемещаем значение из адреса `0x8049a1c` в регистр `%eax`, добавляем единицу и записываем значение обратно в адрес

Проблема в том, что если процесс истратит время выполнения сразу перед записью переменной, то его счётчик (который как мы помним хранится в его изолированном стеке) может рассинхронизироваться с другими счётчиками (других потоков, которые считают верно или даже специально выделенном на стеке) 

Из-за этого, когда этот же поток опять просыпаается, он либо перезаписывает правильное значение в других счётчиках на своё рассинхронизированное, либо просто не добавляет ничего (если отстал на 1) — получается, что программа недосчитывает до предполагаемого значения

Такой пример счётчика называется **критическим участком (Critical section)** программы — это место в коде, которое требует, чтобы к нему имело доступ только ограниченное кол-во потоков (частный случай: один поток за раз, как в примере)
# Примитивы синхронизации
## Атомарные операции

Это концепт операций "Всё или ничего" — операция либо выполняется за раз, либо не выполняется вовсе — без состояния между

Примерами таких могут быть *транзакции* в СУБД или `Atomic` в Go
## Mutex

Он же **Mutual Exclusion** или **Взаимоное исключение** — концепт для самых разных примитивов синхронизации, который ограничивает доступ потока к **критическому участку** программы, если к нему имеет доступ другой поток

Самый простой вид Mutex — это замок (Lock)

```c
pthread_mutex_t lock = PTHREAD_MUTEX_INITIALIZE; // ОБЯЗАТЕЛЬНО инициализировать!
int rc = pthread_mutex_init(&lock, NULL);
assert(rc == 0); // ОБЯЗАТЕЛЬНО проверить получение замка!
x = x + 1; // критический участок
pthread_mutex_unlock(&lock);
```

Такой замок выдаётся одному потоку при заходе в критический участок программы. Другие потоки, которые пытаются туда зайти, зависают в ожидании освобождения замка

Для сигнализирования освобождения нужно использовать соответствующие **условия (condition variables)**

```c
pthread_mutex_t lock = PTHREAD_MUTEX_INITIALIZER;
pthread_cond_t cond = PTHREAD_COND_INITIALIZER;

Pthread_mutex_lock(&lock);
while (ready == 0)
	Pthread_cond_wait(&cond, &lock);
Pthread_mutex_unlock(&lock);
```

В данном коде мы используем функцию-обёртку `Pthread_cond_wait`, которая усыпляет поток, до получения сигнала об изменении статуса замка (достаточно простого сигнала о том, что что-то изменилось). С другой стороны код, который будит поток будет выглядеть как-то так:

```c
Pthread_mutex_lock(&lock);
ready = 1;
Pthread_cond_signal(&cond);
Pthread_mutex_unlock(&lock);
```

Далее:
- Если поток смог взять замок, то флаг `ready` переключится на 1 и поток войдёт в критический участок
- Если нет, то флаг `ready` останется неизменным и поток снова уснёт

> [!CAUTION] Всегда используй условные переменные API 
> Простые флаги не усыпят поток и будут впустую тратить процессорное время, а также могут привести к неочевидным ошибкам — API многопоточности куда предсказуемее
